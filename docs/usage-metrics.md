# Dictation usage

Open Dictation usage below the main window's recording hints. The separate native window has dictation-count, original recording minutes and request-cost charts, daily, weekly and monthly calendar buckets, current day/week/month totals, a date range and a provider filter. It includes Parakeet and Whisper local inference as well as Cloudflare, Hugging Face and OpenRouter. Narrow windows stack the range and provider controls.

## Local records

The app writes `~/Library/Application Support/OSW Cloud/usage-metrics-v1.json`. Each dictation has an ID, recording date, original audio seconds when readable, engine, provider and model. Each processing run has its own ID, timestamp and outcome. Each observed request attempt has its own ID, run/dictation IDs, send/completion dates, provider, model, phase, uploaded seconds when applicable, HTTP status and cost classification. The file contains no credentials, endpoint URLs, transcript text, error bodies, filesystem paths or recording bytes. Writes use a locked cache and same-directory atomic rename, with a mode 0600 file and a mode 0700 new directory.

The service measures the source audio before conversion or speed adjustment. Minutes use that original duration, including failed transcription and empty recognition, not the shorter upload. Reprocessing the same recording keeps its dictation ID and does not add minutes again. Each new run and request still adds its own outcome and cost. Completion is idempotent by run/request ID. Audio cancelled before submission and discarded subminimum captures are not submitted dictations and do not enter this ledger.

The count chart uses the existing dictation records, one count per distinct ID, including recorded failures, empty recognition, unknown durations and local engines. It is not a microphone-start counter. The ledger begins when the transcription service submits a recording for processing, before conversion and inference; cancelled or subminimum captures never reach that point. A storage failure can leave persisted counts incomplete, as the dashboard warning states. No historical starts or unrecorded failures are inferred. Duplicate IDs do not increase counts. Count ticks are integers, including the empty and single-dictation cases. The same calendar buckets and provider/date filters drive all three charts. There is no separate model filter in the existing dashboard; model metadata remains in the dictation/request details.

Immediate recordings use the original file's creation date. Queued recordings use the existing recording date. A dictation's minutes belong to its first tracked engine/provider and recording date. Request costs belong to their own provider and send date. A retry with a different provider can therefore appear in that provider's cost chart without adding original minutes there. Requests identify the encoded cloud route if settings change while the service loads duration. Local model metadata uses a filename or Parakeet version, never a full model path.

Existing recordings, preferences and Worker totals are not imported into the ledger. Reprocessing an existing recording starts tracking its newly observed execution; it does not reconstruct earlier providers or charges. The legacy Worker readout remains separate and explicitly labels Worker uploads and the UTC account window. Direct API no longer displays a Worker-only unavailable usage request. No server changes or deployment are required.

Missing durations and missing costs remain unavailable. In-flight requests left by an interrupted process retain unknown cost and display as in flight or interrupted. A corrupt or unsupported-version file is preserved and shows an error instead of being overwritten. A write failure does not stop dictation, but the dashboard warns that totals may be incomplete. Once another write succeeds, the archive keeps that incompleteness marker across restarts.

## Costs

Reported and estimated dollar amounts are separate subtotals and chart series. Unknown costs have a separate request count, never a zero charge. The request-details list includes cleanup, failures and retries, exact model IDs, classification and source. Dictation details show local runs and their outcomes. Local inference adds minutes but no cloud API request. Any cloud cleanup observed inside the dictation task would still add its own provider request.

OpenRouter's `usage.cost` is a provider-reported USD amount, including an explicit zero. The app accepts a finite, nonnegative numeric charge from transcription, cleanup or error responses. Missing, null, boolean, string and negative values remain unknown. It does not guess a token/audio rate when response usage is missing. Current schema source, checked 2026-10-01: https://openrouter.ai/docs/api/api-reference/stt/create-transcription. Hugging Face does not supply a usable request charge in these routes; hardware compute time is not an audio-minute rate, so costs remain unknown rather than using a Whisper list-rate guess.

Cloudflare transcription estimates use the successful request's uploaded duration, not original minutes. The gross list rates checked 2026-10-01 are USD 0.0052 per audio minute for `@cf/deepgram/nova-3`, USD 0.0005 for `@cf/openai/whisper-large-v3-turbo` and USD 0.0005 for `@cf/openai/whisper`. Source: https://developers.cloudflare.com/workers-ai/platform/pricing/#audio-model-pricing. The rate, date and source travel with each estimate. These are not invoice charges and do not subtract an account-wide free allowance or credits. Tiny English, cleanup without reported charges/verified usage, failed sends and missing usage remain unknown. Cloudflare neuron-based account totals are not attributed as actual per-dictation charges.

Worker mode is an older opaque pipeline. Its existing response exposes observed cleanup execution, not cleanup usage/charges. A returned cleanup is recorded separately with unknown cost. When a Worker response is lost or omits execution evidence, the pipeline attempt remains unknown rather than claiming to know how many inner calls ran. No unavailable Worker-internal retries are invented. Client-side sends and recording reprocessing each get distinct attempt/run IDs; the app does not add a new retry policy.

## Calendar rules

Dates are stored as absolute timestamps. Aggregation uses the current Mac calendar, timezone and first weekday. Calendar date intervals handle local midnight, month/year boundaries and 23/25-hour daylight-saving days; periods are not fixed-duration multiples of 24 hours. Range endpoints are half-open internally, while custom Through dates include the selected whole local day. A recording crossing midnight belongs wholly to its recording date; a request crossing midnight belongs to its send date. Selecting another timezone changes calendar buckets, not saved timestamps.

## Validation

Run `python3 scripts/patch_osw.py`, `npm test`, `scripts/test_shortcuts.sh` and `scripts/build_app.sh`. The build only creates the candidate under the worktree; it does not install it or reset permissions. `scripts/test_usage.sh` compiles production metrics and all three production cloud clients, tests stubbed request responses without real keys or network inference, and typechecks the native chart view. With generated source present, it also compiles the actual TranscriptionService with isolated engine doubles and an injected usage store, then checks fresh/idempotent patch generation.

Deterministic cases cover original versus 1.5x uploaded duration, recording identity and retries, failure/success outcomes, local inference, cleanup-only costs, mixed providers, exact zero versus unknown charges, error-response charges, transport failure, interrupted requests, duplicate completions, restart persistence, file modes, privacy, corruption, write failures, concurrent writes, serialized queue/indicator decoding across the duration await, provider filtering, half-open ranges, daily/weekly/monthly totals, year boundaries and both DST transitions.

Committed native captures use isolated sample ledgers, not user history: [normal](../attachments/usage-dashboard/normal.png), [narrow](../attachments/usage-dashboard/narrow.png), [monthly](../attachments/usage-dashboard/monthly.png) and [empty](../attachments/usage-dashboard/empty.png).

For safe native UI inspection, compile `src/client/UsageMetrics.swift`, `src/client/UsageDashboard.swift` and `scripts/usage_ui_probe.swift` with `swiftc -O -parse-as-library`, then run the executable with an output directory inside this worktree and a mode of `normal`, `narrow`, `empty`, `filtered`, `weekly` or `monthly`. It opens and rasterizes the production view in a native window with an isolated sample ledger, without preferences, engines, input taps, microphone, credentials or paid calls. These are native view captures, not evidence of physical microphone, hotkey-to-paste or the installed app's full startup flow.
